# Study Sessions Model Design

## 1. Purpose

The study sessions model manages planned blocks of study time. Each session belongs
to one student and can optionally be associated with an assignment.

## 2. Data Structure

| Field           | Type    | Required | Description                                 |
| --------------- | ------- | -------- | ------------------------------------------- |
| id              | UUID    | Yes      | Unique identifier generated by the database |
| studentId       | UUID    | Yes      | Student who owns the session                |
| assignmentId    | UUID    | No       | Related assignment, if any                  |
| title           | String  | Yes      | Name of the study session                   |
| subject         | String  | No       | Subject or course being studied             |
| scheduledAt     | Date    | Yes      | Date and time the session is scheduled      |
| durationMinutes | Integer | Yes      | Planned session duration in minutes         |
| createdAt       | Date    | Yes      | Date the record was created                 |
| updatedAt       | Date    | Yes      | Date the record was last updated            |

Database defaults provide the session UUID and timestamps. The database enforces
the student and optional assignment foreign keys; removing a linked assignment
sets `assignmentId` to null without removing the session.

## 3. Model Operations

`createStudySessionModel` accepts the configured database client and exposes:

- **Get:** Retrieve all study sessions.
- **Store:** Create a session and return the inserted record.
- **Find by student ID:** Retrieve all sessions belonging to a student.
- **Find by ID:** Retrieve one session, or `null` if it does not exist.
- **Update:** Update provided session fields and its `updatedAt` timestamp; return
  the updated record, or `null` if it does not exist.
- **Remove:** Delete a session and return the deleted record, or `null` if it does
  not exist.

Database errors (including invalid UUIDs and constraint violations) are allowed
to propagate to the caller.

## 4. Types and Integration

`StudySession`, `StoreStudySessionInput`, and `UpdateStudySessionInput` are derived
from the Drizzle table definition to keep model inputs and returned records aligned
with the database. The model uses Drizzle ORM and dependency injection so production
uses PostgreSQL and tests can use PGlite.

Student ownership authorization remains the responsibility of the authenticated
server operation that calls the model.

## 5. Testing

Vitest with an in-memory PGlite database verifies listing, creation, retrieval by
ID and student, updates, deletion, missing records, and unlinking a session when
its associated assignment is removed.
